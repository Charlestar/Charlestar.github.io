## 1. 稀疏激活不等于低显存

MoE 层为每个 token 选择少数专家，因此每 token 的计算量小于激活全部专家；但若不做卸载，所有专家权重仍需驻留在设备集合中。MoE 的主要收益是以较低激活计算扩大参数容量，而不是让总参数免费消失。

典型路由可写为：

$$y=\sum_{i\in\operatorname{TopK}(g(x))}p_i(x)E_i(x)$$

路由还需处理容量、负载不均和丢弃/重路由策略。Top-k、共享专家和负载均衡方法因模型而异。

## 2. 专家并行的数据路径

```text
tokens -> router -> dispatch / all-to-all
                   -> local expert GEMMs
        <- combine / all-to-all <-
```

专家并行把不同专家放到不同 rank。瓶颈往往从 GEMM 转向 token dispatch、all-to-all、负载倾斜和小矩阵效率，因此需要 grouped GEMM、通信/计算重叠与拓扑感知放置。

## 3. 关键优化

- **负载均衡**：测每专家 token 数、最大/平均负载比与尾部通信时间。
- **量化**：权重/激活精度、kernel 可用性和质量需一起验证；“FP8 一定快 1.8×”不成立。
- **专家卸载**：降低 HBM 占用但引入 CPU/存储传输，适合命中分布稳定或容量优先场景。
- **并行组合**：TP、EP、DP 的最优组合受模型和互联拓扑影响。
- **MTP/推测解码**：可减少目标模型串行步数，但收益由接受长度和验证效率决定。

## 4. 部署指标

除 TTFT、TPOT、吞吐和显存外，MoE 还应监控：每专家负载、dispatch/combine 时间、all-to-all 带宽、被丢弃 token、grouped GEMM shape 与跨节点流量。

## 5. 结论

MoE 部署是计算、容量与通信的联合优化。任何硬件数量建议都必须绑定模型 checkpoint、精度、上下文、并发和目标 SLO；不能把一张未经说明的吞吐表当作采购依据。

## 6. Router 与容量约束

router 为每个 token 产生 expert scores，经 softmax 后选 top-k。训练时常加入负载均衡目标；推理时若某专家收到过多 token，系统可能 padding 到统一容量、丢弃溢出 token，或使用不丢弃的动态 shape。不同模型定义不同，serving 不能擅自修改策略而假设质量不变。

常见观测量：

$$load\_ratio_i=\frac{tokens\ routed\ to\ expert\ i}{total\ routed\ tokens}$$

最大值、标准差和 top-k overlap 能帮助定位热点专家。

## 7. Dispatch 与 grouped GEMM

路由后 token 需要按 expert 重排：

```text
original token order
 -> histogram / prefix sum by expert
 -> permute tokens
 -> grouped GEMM for variable expert batches
 -> weighted combine
 -> inverse permutation
```

小 batch 下很多专家只收到少量 token，GEMM 形状过小；大 batch 提高效率，却可能增加延迟。Grouped GEMM 把多个专家矩阵乘组织在一个调度中，减少 launch 开销并改善利用率。

## 8. All-to-all 通信量

Expert Parallel 下，每个 rank 把 token hidden states 发给拥有目标 expert 的 rank，再把输出发回。通信量近似与 token 数、hidden size、dtype 和 top-k 成正比。跨节点网络显著慢于节点内 NVLink，因此专家放置和 EP group 边界很重要。

## 9. 显存拆解

总显存至少包含全部本地专家权重、shared experts、attention 权重、KV Cache、临时 dispatch buffer、CUDA Graph pool 和通信 buffer。只用“激活参数量 × 字节”估算会严重低估部署需求。

## 10. 调优顺序

先确认正确路由与质量，再看专家负载；随后测 grouped GEMM 与 all-to-all 占比；最后调整并行度、量化和通信重叠。一次同时改变 EP、dtype、batch 和 kernel，会让收益来源无法解释。
